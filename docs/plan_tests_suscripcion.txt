PLAN DE TESTS - FLUJO DE SUSCRIPCION
Fecha: 2026-03-16

Objetivo
- Validar que no se cree tenant antes de suscripcion activa.
- Validar ruteo por estado de suscripcion.
- Validar endurecimiento minimo de reglas para billing/access.

Cobertura automatizada implementada
1) Logica de estados/ruteo:
   - Archivo: functions/tests/subscriptionDomain.test.js
   - Valida:
     - mapping MP -> billing interno
     - normalizacion de billing.status
     - nextRoute para perfil activo / sin pago / rechazado / sin perfil

2) Guardas de seguridad en reglas (test estatico):
   - Archivo: functions/tests/firestoreRules.static.test.js
   - Valida que firestore.rules contenga:
     - bloqueo write cliente en /billingAttempts
     - bloqueo read/write cliente en /billingEvents
     - /billingPlans solo lectura cliente
     - preservacion de tenantId, billing, access y onboarding en /usuarios

Comando de ejecucion
- Desde raiz del repo:
  npm --prefix functions run test:subscription

Nota:
- Este set automatizado cubre los riesgos mas criticos de routing/estado y seguridad de reglas.
- Los casos con Mercado Pago real y concurrencia quedan cubiertos por plan manual.

====================================================================
MATRIZ MANUAL DETALLADA (CASOS 1-10)
====================================================================

Datos de prueba recomendados
- Usuario nuevo A: u_test_aprobado@abc.gob.ar
- Usuario nuevo B: u_test_rechazado@abc.gob.ar
- Usuario existente sin pago C: u_test_sin_pago@abc.gob.ar
- Tenant esperado: se crea solo en estado active

Caso 1. usuario nuevo -> pago aprobado
Precondicion:
- No existe /usuarios/{uid} para A.
Pasos:
1. Registrar usuario A en /registro.html
2. Ejecutar checkout y completar pago aprobado en MP.
3. Esperar webhook (o usar sync manual en estado-suscripcion).
Validar:
- /usuarios/{uid}.billing.status == "active"
- /usuarios/{uid}.access.appEnabled == true
- /usuarios/{uid}.tenantId no vacio
- Existe /tenants/{tenantId} con ownerUid == uid
- Login redirige a /horarios.html

Caso 2. usuario nuevo -> pago rechazado
Precondicion:
- No existe /usuarios/{uid} para B.
Pasos:
1. Registrar usuario B.
2. Iniciar checkout y forzar rechazo en MP.
3. Esperar webhook o sync.
Validar:
- billing.status en "rejected" (o equivalente no activo)
- access.appEnabled == false
- tenantId sigue null/vacio
- Login redirige a /estado-suscripcion.html

Caso 3. usuario existente sin pago -> login
Precondicion:
- /usuarios/{uid} existe con billing.status null y appEnabled false.
Pasos:
1. Login (Google o email) con C.
Validar:
- Redireccion a /activar-plan.html
- No se crea tenant nuevo durante el login

Caso 4. falla startSubscriptionCheckout luego de registerUser
Precondicion:
- Usuario nuevo listo para registrar.
Pasos:
1. Simular falla en startSubscriptionCheckout (secret MP faltante o error forzado).
2. Ejecutar registro.
Validar:
- Usuario Auth queda creado
- /usuarios/{uid} existe
- tenantId sigue null
- access.appEnabled == false
- Mensaje UI indica recuperacion desde /activar-plan.html

Caso 5. multiples clicks en Suscribirme
Precondicion:
- Usuario con appEnabled false.
Pasos:
1. Click rapido 2-3 veces en boton "Suscribirme".
2. Revisar /billingAttempts.
Validar:
- Se crean multiples intentos
- Solo uno queda isCurrent == true (el ultimo)
- billing.lastAttemptId del usuario coincide con ultimo intento

Caso 6. webhook duplicado
Precondicion:
- Existe intento + preapprovalId activo.
Pasos:
1. Reenviar mismo webhook 2 veces (o replay desde logs).
Validar:
- No se duplica tenant
- No cambia ownerUid
- billingEvents registra recepcion y procesamiento sin efectos duplicados

Caso 7. webhook perdido + sync manual
Precondicion:
- Pago aprobado en MP, webhook no entregado.
Pasos:
1. Entrar a /estado-suscripcion.html
2. Click "Sincronizar estado"
Validar:
- sync actualiza billing.status a active
- Se crea tenant si faltaba
- appEnabled pasa a true
- nextRoute /horarios.html

Caso 8. usuario activo cambia de dispositivo
Precondicion:
- Usuario con suscripcion active y tenant existente.
Pasos:
1. Login desde navegador/dispositivo nuevo.
Validar:
- Estado se obtiene desde Firestore
- Acceso directo a /horarios.html
- Banner muestra Plan Pro

Caso 9. webhook + sync manual concurrente
Precondicion:
- Suscripcion en transicion (pending -> active).
Pasos:
1. Disparar sync manual mientras llega webhook.
2. Repetir 2-3 veces.
Validar:
- Estado final consistente en usuario e intento
- Tenant unico (sin duplicados)
- Sin errores de consistencia (ownerUid/tenantId)

Caso 10. reglas bloquean escritura indebida sobre billing/access
Precondicion:
- Usuario autenticado normal en cliente.
Pasos:
1. Intentar set/update directo desde frontend sobre /usuarios/{uid}:
   - billing.status
   - access.appEnabled
   - onboarding.subscriptionActivated
   - tenantId
2. Intentar write en /billingAttempts y /billingEvents.
Validar:
- Firestore responde PERMISSION_DENIED en todos esos intentos
- Updates de perfil permitido (nombre/contacto/correoAlt/etc.) siguen funcionando
