0) AJUSTES APROBADOS (DESDE docs/mejoras.txt)
==================================================================

Se incorporan estos ajustes:

1. Usuario base con `billing.planCode = null` y `billing.status = null`.
2. `pending_checkout` solo se usa despues de iniciar checkout real.
3. Politica de intentos: cada `startSubscriptionCheckout` crea intento nuevo (los anteriores quedan obsoletos para routing).
4. Vinculo de lookup rapido a intento/preapproval desde usuario (`billing.lastAttemptId` y `billing.mpPreapprovalId`).
5. `billingEvents` con `autoId`; no usar solo `x-request-id` como ID de doc.
6. Orden de webhook definido para ACK rapido y procesamiento robusto.
7. `syncSubscriptionStatus` con fallback si falta `mpPreapprovalId` en usuario.
8. `ensureBillingActivation` agrega timestamps de activacion/provision.
9. Routing frontend cerrado con tabla estricta por estado.
10. Reglas Firestore con campos de usuario editables separados de campos sensibles.
11. Politica de migracion para usuarios/tenants huerfanos con revision manual.

4.3 `startSubscriptionCheckout` (callable nueva)
Input:
{
  "planCode": "plan_pro"
}
Politica de intentos:
- Cada invocacion crea un `billingAttempt` nuevo.
- Intentos anteriores quedan auditados y se marcan `isCurrent = false`.

Acciones:
- validar auth
- validar plan activo en `/billingPlans/plan_pro`
- crear intento en `/billingAttempts`
- crear preapproval en MP
- actualizar `/usuarios/{uid}`:
  - `billing.planCode = "plan_pro"`
  - `billing.status = "pending_checkout"`
  - `billing.lastAttemptId = "<attemptId>"`
  - `billing.mpPreapprovalId = "<mpPreapprovalId>"`
  - `onboarding.checkoutStarted = true`
- devolver `initPoint`

4.4 `mercadoPagoWebhook` (HTTP nueva)
Orden obligatorio:
1. recibir request
2. extraer headers y payload
3. validar firma
4. persistir evento en `billingEvents` (autoId)
5. responder `200` inmediatamente
6. continuar procesamiento en worker/cola interna:
   - resolver `preapprovalId`
   - consultar estado real a MP
   - mapear estado interno
   - actualizar attempt + usuario
   - activar tenant si corresponde

Nota tecnica:
- No depender de ejecutar logica pesada despues de `res.send(200)` en el mismo request.
- Usar cola/worker (por ejemplo Cloud Tasks / PubSub / re-dispatch interno).

4.5 Mapping de estado MP -> estado interno

Definir helper explicito en backend:
- `authorized` -> `active`
- `pending` -> `pending_confirmation`
- `paused` -> `paused`
- `cancelled` -> `cancelled`
- `rejected` -> `rejected`
- `expired` -> `expired`
- desconocido/error -> `error`

Nota: ajustar nombres exactos segun payload real de MP en produccion.

Uso: soporte manual / boton "ya pague, reintentar sincronizacion".

Acciones:

- actualizar estado local
- activar tenant si corresponde

9) MATRIZ DE PRUEBAS OBLIGATORIA
==================================================================

1. Usuario nuevo -> pago aprobado:
- crea tenant
- habilita acceso
- muestra Plan Pro

2. Usuario nuevo -> pago rechazado:
- no crea tenant
- queda en estado-suscripcion

3. Usuario existente sin pago -> login Google:
- redireccion a activar-plan/estado-suscripcion

4. Falla `startSubscriptionCheckout` luego de `registerUser`:
- usuario queda bloqueado, sin tenant
- puede reintentar desde activar-plan

5. Multiples clicks en Suscribirme:
- se crean multiples intentos
- solo ultimo intento queda `isCurrent = true`

6. Webhook duplicado:
- no duplica tenant ni activacion

7. Webhook perdido:
- `syncSubscriptionStatus` recupera estado correcto

8. Usuario activo cambia de dispositivo:
- estado se toma de Firestore y entra normal
