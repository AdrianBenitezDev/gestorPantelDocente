Ajustes finos que todavía haría
1. En /usuarios/{uid}, billing.status = "pending_checkout" desde el alta base puede inducir ruido

No está mal, pero semánticamente puede ser raro si el usuario se creó y todavía nunca inició checkout.

Yo lo dejaría así:

opción más precisa

al crear usuario base:

billing.planCode = null

billing.status = null

onboarding.checkoutStarted = false

y recién en startSubscriptionCheckout:

billing.planCode = "plan_pro"

billing.status = "pending_checkout"

onboarding.checkoutStarted = true

Porque pending_checkout sugiere que ya existe un intento.
Si todavía no hubo intento, null o not_started representa mejor la realidad.

Si querés mantenerlo simple, podés dejarlo como está, pero a nivel diseño yo prefiero esa separación.

2. startSubscriptionCheckout debería definir qué hace con intentos anteriores abiertos

Eso ahora no está explícito.

Ejemplo:

el usuario aprieta “Suscribirme”

genera intento A

vuelve atrás

aprieta otra vez

genera intento B

Eso puede estar bien, pero necesitás una política.

Yo definiría una de estas dos:

política A: siempre crear un nuevo intento

se crea nuevo billingAttempt

el anterior queda viejo/inactivo

política B: reutilizar último intento si sigue vigente

si el último intento todavía sirve, se reutiliza initPoint

Para evitar quilombo, te recomiendo política A, pero documentala:

cada invocación de startSubscriptionCheckout crea un nuevo intento; los anteriores quedan obsoletos para routing interno, aunque puedan seguir auditados.

4. mercadoPagoWebhook debería dejar explícito el orden interno ideal

Ahora dice:

validar firma

guardar auditoría

consultar estado real

actualizar

responder 200 rápido

Eso está bien conceptualmente, pero el orden conviene dejarlo más claro para no implementarlo mal.

Yo lo escribiría así:

recibir request

extraer headers y payload

validar firma

persistir evento recibido en billingEvents

responder 200 inmediatamente

continuar procesamiento interno:

resolver preapprovalId

consultar a MP

mapear estado

actualizar intento y usuario

activar tenant si corresponde

Porque si ponés “responder 200 rápido” al final, algún dev puede terminar devolviendo 200 demasiado tarde.

5. syncSubscriptionStatus debería poder funcionar aunque falte mpPreapprovalId en usuario

Caso real:

usuario quedó medio inconsistente

usuarios/{uid}.billing.mpPreapprovalId está vacío

pero en billingAttempts sí está

Entonces esta callable debería buscar:

usuarios/{uid}.billing.mpPreapprovalId

si no existe, último billingAttempt del usuario con mpPreapprovalId

si no hay nada, devolver error funcional tipo:

subscription_not_found

Eso te da resiliencia.

6. En migración, agregaría una política explícita para usuarios “huérfanos”

Muy importante.

Tenés que decidir qué hacer con casos como:

usuario con tenant pero sin owner claro

usuario con tenant pero sin membresía

tenant sin datos base mínimos

Yo agregaría una regla así:

Los usuarios históricos con tenant válido y uso operativo conservan acceso.
Los casos inconsistentes detectados por script de migración se envían a una lista de revisión manual y no se corrigen automáticamente si hay riesgo de asignación errónea.

Eso te protege de tocar datos reales incorrectamente.

9. Reglas de Firestore: te falta aclarar si el cliente puede escribir algo de /usuarios/{uid}

Decís:

puede leer su propio /usuarios/{uid}

Perfecto. Pero faltaría definir si puede escribir algo.

Mi recomendación:

cliente no escribe campos de billing/access/onboarding críticos

si necesita actualizar perfil, que sea en campos permitidos y bien separados

Por ejemplo:

/usuarios/{uid} con campos sensibles solo backend

/usuarios/{uid}/preferences/... o campos puntuales editables por cliente

Porque si no, podrías dejar una puerta abierta para que el cliente altere estados accidentalmente.

obligatorio 1

No usaría pending_checkout en usuario base si todavía no hubo checkout real.
Pondría null o not_started.

obligatorio 2

Documentaría política de múltiples billingAttempts.

obligatorio 3

Aclararía mejor qué campos de /usuarios/{uid} son solo backend y cuáles puede tocar el cliente.
