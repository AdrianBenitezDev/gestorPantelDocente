PLAN DE CAMBIOS - PAC PROCESADOS A EXCEL
Fecha: 2026-05-12

Objetivo funcional pedido (ajustado)
1) En pac-procesados.html, mostrar rows sin depender de "Ver detalle".
2) Cada row debe tener checkbox para seleccion.
3) Con boton "Crear PAC", enviar rows seleccionadas y terminar en Excel.
4) Ambos caminos (Gmail y PAC procesados) deben terminar en:
   - tabla renderizada de datos útiles para Excel,
   - seleccion de rows,
   - creacion/descarga de Excel.
5) Revisar paneldocente-email-worker para guardar los datos ya en formato de uso frontend,
   evitando normalizaciones en panelDocente.

Resumen tecnico del estado actual
- Worker (paneldocente-email-worker/src/index.js):
  - Extrae row con: cupof, cuil, dni, fechaNacimiento, apellidoNombre, situacionRevista,
    pid, cargoModulosHoras, curso, division, + metadata.
  - Envia payload rows al webhook Firebase (ingestPacForwardedEmail).
- Frontend Gmail (frontend/js/pac.js):
  - Para render/clipboard divide CUIL en partes y deriva modCarr (splitCuilParts, deriveModCarr).
- Backend panelDocente (functions/src/index.js):
  - Para Excel vuelve a dividir CUIL y derivar modCarr en pacBuildSheetValues.
  - getProcessedPacList hoy devuelve resumen (sin rows completas).

Problema raiz
- El contrato de datos no es "frontend-ready":
  - Se guarda cuil unificado y luego se recalcula cuilPrefix/cuilSuffix.
  - Se guarda curso y luego se recalcula modCarr.
- Resultado: normalizacion/derivacion repetida entre worker, frontend y backend.

AJUSTES FINALES RECOMENDADOS

1) Agregar rowFormatVersion obligatorio
- En las rows generadas desde paneldocente-email-worker, agregar:
  rowFormatVersion: "v2"
- Este campo debe permitir diferenciar filas nuevas con contrato canónico de rows legacy.
- El frontend y el backend deben usar este campo solo como referencia de compatibilidad, sin romper filas antiguas.

2) Agregar rowId estable para seleccion
- En pac-procesados, cada row renderizada debe tener un identificador estable para checkbox y seleccion.
- Si el backend no envia un ID propio, generar uno en frontend con:
  __rowId: `${docId}_${index}`
- Usar ese ID para selectedRowIds, seleccion individual, seleccionar todo y deseleccionar todo.

3) Separar metadata de datos útiles para Excel
- No mezclar metadata del correo con los campos que se usan para completar la planilla.
- Mantener una estructura conceptual similar a:
  {
    row: { ...datosCanonicosExcel },
    metadata: { subject, from, date, attachmentName, source }
  }
- La tabla principal debe mostrar solamente datos útiles para Excel.
- La metadata puede mostrarse en un bloque secundario de metadata de auditoría/contexto.

4) Mantener compatibilidad con rows legacy
- Si una fila antigua no tiene cuilPrefix, cuilSuffix o modCarr, mantener fallback:
  - dividir CUIL desde cuil completo
  - derivar modCarr desde curso
- No romper PAC ya procesados previamente.

Objetivo de estos ajustes:
- Consolidar el contrato canónico de rows.
- Evitar normalizaciones repetidas.
- Mejorar seleccion de filas.
- Mantener compatibilidad con datos antiguos.
- Separar claramente datos de Excel y metadata de auditoría.

LIMITE DEFENSIVO DE ROWS

- Cuando getProcessedPacList se invoque con includeRows=true, debe existir un limite defensivo de rows por item.
- Definir rowsPerItemLimit con valor default recomendado: 300.
- Definir un maximo duro permitido recomendado: 1200.
- Si el frontend solicita un valor mayor al maximo duro, el backend debe limitarlo automaticamente.
- Este limite evita payloads excesivos, problemas de memoria, lentitud en frontend y respuestas demasiado grandes desde Firestore/Firebase Functions.
- Mantener compatibilidad con el flujo actual: includeRows=false debe seguir devolviendo solo resumen.
- Si en el futuro se necesitan PAC muy grandes, evaluar paginado de rows o carga progresiva por documento.

Objetivo de esta seccion:
- Proteger performance.
- Evitar sobrecarga de frontend/backend.
- Mantener escalabilidad para muchos PAC procesados.
- Dejar preparado el camino para paginado o virtualizacion futura.
